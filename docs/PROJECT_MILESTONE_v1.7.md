## 一、项目定位

本项目是一个“修仙 MMO / 放置养成类”网页游戏。

核心目标不是简单堆系统，而是做出一个有修仙世界味道、长期可玩、玩家有自主选择空间的开放世界养成游戏。

项目当前重点：

1. 完成核心养成循环。
2. 做出宗门、探索、生活技能、目标链等基础系统闭环。
3. 保持所有核心逻辑后端化、数值配置化。
4. 逐步进入真实玩家试玩阶段，收集反馈。
5. 后续探索更有独立游戏突破性的“玩法灵魂”，例如一命修仙、分魂重生、夺舍、轮回、唯一高阶法宝、拍卖、链上唯一资源等。

---

## 二、当前核心设计原则

后续所有任务必须继续遵守以下原则：

1. 所有核心逻辑必须在后端。
2. 所有玩家行为必须走统一接口 `/action/execute`。
3. 所有数值集中在 `configs` + `calc_service`。
4. 所有内容必须可配置。
5. 不允许出现单一最优玩法。
6. 探索是核心资源来源。
7. 法力是唯一行动资源。
8. 气运、心魔等隐藏属性不能直接展示给玩家。
9. 任务系统不能卡死。
10. 玩家可见内容必须中文。
11. 不允许出现裸 `item_id` / `task_id` / `sect_task_xxx`。
12. 接口测试通过不等于玩家可用，必须真实浏览器点一遍。
13. 项目定位是开放世界，不做强制引导，不做自动寻路刷经验/等级。
14. 系统可以推荐，但不能替玩家做决定。
15. 首页目标链只能作为友好提醒，不是主线任务、每日任务或强制路线。

## 三、当前协作分工

### 1. 用户

角色：主决策者、游戏设计者、系统设计者、数值方向把关者。

主要负责：

- 决定游戏方向。
- 判断玩法是否有趣。
- 判断系统是否符合修仙世界观。
- 判断是否进入下一阶段。
- 选择是否合并、发布、给真实玩家试玩。

用户不希望陷入大量低级技术操作，希望 AI 和 Agent 尽量承担：

- 代码修改。
- 测试。
- Git 操作。
- 浏览器验收。
- 问题定位。
- 文档整理。

### 2. ChatGPT

角色：项目大脑、玩法设计、系统拆解、任务包编写、审查提示词、里程碑总结。

主要负责：

- 把用户想法整理成可执行任务包。
- 制定系统设计和边界。
- 审查 MiniMax / Codex 的反馈是否可信。
- 判断任务是否可以合并。
- 维护项目长期方向和上下文。
- 在关键节点整理项目更新文档。

ChatGPT 不直接承担本地代码执行，但负责把任务写清楚，降低用户和 Agent 的沟通成本。

### 3. MiniMax Agent

当前定位：主力实验开发 Agent。

主要负责：

- 在 feature / bugfix 分支上开发。
- 修改代码。
- 本地跑测试。
- 浏览器验收。
- 根据 Codex 审查意见回修。
- push feature 分支。

当前评价：

MiniMax 整体表现明显优于 OpenClaw，能理解任务、执行测试、根据审查回修。但仍需 Codex 守门，因为曾出现过浏览器验收不够严格的问题。

### 4. Codex

当前定位：最终审查与合并守门员。

主要负责：

- 独立审查 MiniMax 的实现。
- 独立跑测试。
- 独立真实浏览器验收。
- 检查是否存在玩家路径问题。
- 判断是否可合并 main。
- 执行 main 合并。
- 打稳定 tag。
- push main / tag。

Codex 是最终质量门禁，MiniMax 完成不代表可以直接合并。

### 5. OpenClaw

当前定位：暂停 / 放弃作为主力。

原因：

- 历史上多次漏测。
- 报告矛盾。
- 未 push 或状态说明不可靠。
- 玩家路径验收不足。
- 完成声明可信度较低。

后续最多作为低风险备用，不再分配关键开发任务。

## 七、MiniMax 使用经验与问题

### 当前优点

MiniMax 当前适合作为主力开发 Agent。

表现较好的方面：

- 任务理解能力较好。
- 能按任务推进。
- 能跑测试。
- 能补浏览器验收。
- 能根据 Codex 审查意见快速回修。
- 报告结构清晰。
- Git 纪律比 OpenClaw 更可控。

### 已发现问题

1. MCP / 浏览器工具 JSON 参数曾卡住。
2. 本地 VPN / TUN 有时会导致普通任务卡顿。
3. 初次浏览器验收可能不够严格。
4. 有时只验证页面显示，没有验证玩家是否能完成完整流程。
5. GitHub push / fetch / pull 需要 VPN / TUN。

### 当前固定经验

MiniMax 本地开发、跑测试、浏览器验收：

- 建议关闭 VPN / TUN，更快更稳定。

MiniMax GitHub 操作：

- 需要开启 VPN / TUN。

推荐流程：

1. 本地开发 / 测试 / 浏览器验收：关闭 VPN / TUN。
2. GitHub fetch / pull / push：开启 VPN / TUN。
3. 如果 GitHub 连接失败，先检查 TUN。

### 当前要求

1. 独立测试。
2. 独立浏览器验收。
3. 检查玩家路径是否真的可完成。
4. 检查是否有临时文件混入提交。
5. 检查 Git 状态。
6. 合并 main 前后都要确认 commit / tag / push 状态。

### 常见 GitHub 问题

如果出现：

- `Recv failure: Connection was reset`
- `Failed to connect to github.com port 443`
- `Empty reply from server`

优先判断：

用户可能忘记打开 VPN / TUN。

处理方式：

1. 打开 VPN / TUN。
2. 等待 10-20 秒。
3. 重新执行 `git fetch` / `git pull` / `git push`。

在给真实玩家试玩前，建议先做一个 `public-playtest-readiness` 分支或任务包。

检查内容：

1. 新账号注册 / 登录是否顺畅。
2. 首页首屏是否清楚。
3. 是否存在英文、裸 ID、内部字段。
4. 是否有明显报错。
5. 是否有危险的开发接口暴露。
6. 是否有调试按钮或测试数据暴露给玩家。
7. 是否有数据库重置方案。
8. 是否能隔离测试玩家数据。
9. 是否有简单反馈入口或反馈收集方式。

## 十一、长期计划

### 1. 真实玩家反馈驱动

下一阶段重点应从“系统有没有做出来”转向“玩家是否愿意继续玩”。

核心问题：

1. 玩家第一次进入是否知道做什么？
2. 5 分钟内有没有成就感？
3. 1 小时内有没有规划目标？
4. 第二天是否有回来看的理由？
5. 是否有收藏欲、成长欲、竞争欲？
6. 修仙世界的残酷感是否成立？
7. 系统是否只是功能堆叠，还是有真正的世界感？

### 2. 开放世界目标感

目标链第一版只是轻量建议。

长期可以发展为：

- 当前境界目标。
- 宗门路线目标。
- 法宝路线目标。
- 生活技能路线目标。
- 探索区域目标。
- 风险事件目标。

但必须保持：

- 不强制。
- 不自动执行。
- 不替玩家做决定。

### 3. 宗门长期化

宗门可以继续扩展：

- 职位晋升。
- 宗门内门 / 外门 / 长老体系。
- 宗门声望。
- 阵营冲突。
- 宗门任务链。
- 宗门战争或秘境争夺。
- 玩家后期建立宗门。

### 4. 世界残酷性与可接受度

用户对革命性玩法有明确兴趣：

- 一命修仙。
- 死亡后分魂重生。
- 夺舍。
- 轮回转世。
- 高阶法宝唯一性。
- 世界资源稀缺。

但这些机制风险很高，需要平衡：

- 残酷真实感。
- 玩家可接受度。
- 失败后的继续动力。
- 付出与损失是否公平。

建议先设计，不急于实现。

## 十二、项目当前主要问题汇总

### 1. 玩家真实体验还没有经过真人验证

目前测试主要来自 Agent 和浏览器验收。

下一阶段必须让真人试玩。

真实玩家可能暴露的问题包括：

- 看不懂系统。
- 不知道下一步做什么。
- 文案太工程化。
- 首屏信息太多或太少。
- 按钮含义不清。
- 成长反馈不够爽。
- 资源获取节奏不舒服。
- 宗门任务目标不明确。

### 2. UI 还可能不适合真实玩家

当前 UI 以功能可用为主。

发布试玩前需要关注：

- 首页布局。
- 操作区优先级。
- 文案友好程度。
- 移动端 / PC 适配。
- 错误提示是否像游戏提示。

### 3. Agent 验收仍需强约束

MiniMax 曾漏掉“捐献任务按钮禁用”这种真实路径问题。

以后任务验收必须明确：

- 不仅看见按钮。
- 必须点击按钮。
- 不仅看见任务。
- 必须完成任务。
- 不仅接口返回 200。
- 必须真实浏览器完成玩家路径。

### 4. Git / VPN 切换影响效率

本地开发和 GitHub 操作对 VPN / TUN 需求不同。

短期可以人工提醒。

长期建议调整 Clash 规则模式，让：

- 本地服务直连。
- GitHub / OpenAI 走代理。

减少反复切换。

### 5. 缺少试玩环境与反馈闭环

下一阶段应建立：

- 公共试玩地址。
- 测试账号或注册入口。
- 简单反馈渠道。
- 玩家行为观察方式。
- 版本更新记录。

## 十三、下一步提高效率建议

### 1. 固定开发流程

建议以后每个功能都按这个流程：

1. ChatGPT 写任务包。
2. MiniMax 在 feature 分支开发。
3. MiniMax 自测 + 浏览器验收。
4. MiniMax push feature 分支。
5. Codex 独立复审。
6. Codex 提出 P0/P1/P2 问题。
7. MiniMax 回修。
8. Codex 复审通过。
9. Codex 合并 main。
10. Codex 打 tag。
11. ChatGPT 更新里程碑文档。

### 2. 固定验收模板

每次 Agent 报告必须包含：

- 当前分支。
- 当前 commit。
- 修改文件列表。
- 是否有临时文件。
- 测试结果。
- 浏览器验收路径。
- 是否发现英文 / 裸 ID。
- 是否影响玩家状态。
- 是否建议合并。
- 是否已 push。

### 3. 任务包要写“反向禁止项”

以后任务包不仅写要做什么，还要写不能做什么。

例如目标链系统必须明确禁止：

- 不发奖励。
- 不一键执行。
- 不自动寻路。
- 不改玩家状态。
- 不显示隐藏属性。
- 不显示内部字段。

这样能减少 Agent 自作主张。

### 4. 重要节点先文档化再继续开发

每完成一个稳定 tag，建议更新一次文档。

尤其是：

- 宗门系统。
- 目标链。
- 公共试玩发布。
- UI 大改。
- 玩法灵魂系统。

### 5. 进入真人试玩后，优先修体验问题

真人试玩阶段不要急着堆新系统。

优先级应调整为：

1. 是否能顺利进入游戏。
2. 是否能看懂首页。
3. 是否知道做什么。
4. 是否有正反馈。
5. 是否有明显卡死。
6. 是否愿意继续点。
